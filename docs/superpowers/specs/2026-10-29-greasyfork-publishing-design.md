# Greasy Fork publishing: design

**Date:** 2026-10-29

**Status:** accepted

**Size:** small change

## Intent

Add Greasy Fork as a FlixMonkey userscript distribution channel without a new
build or browser automation. Greasy Fork has no publish API. Its supported
integration syncs a listing from a GitHub release, so the release publishes the
userscript, Greasy Fork consumes it, and the manual `Publish to Stores` run
confirms that Greasy Fork is serving the released version.

## Goals

- A Greasy Fork listing updates automatically when a FlixMonkey release is
  published.
- `publish-to-stores.yml` gains a `publish-greasyfork` job that performs one
  check of the released userscript and the Greasy Fork listing version, then
  passes or fails. No polling and no retries.
- The one-time Greasy Fork and GitHub webhook setup is documented so a
  maintainer can repeat it.
- `docs/STORE_PUBLISHING.md`, `CONTRIBUTING.md`, and `AGENTS.md` describe the new
  channel and its verification.

## Non-goals

- Uploading through the Greasy Fork web form or driving the site with Playwright.
- Triggering the Greasy Fork update from the manual workflow.
- Polling Greasy Fork until the version appears.
- Changes to `src/targets/userscript/metadata.ts`. Its `@updateURL` and
  `@downloadURL` already point at the release asset that Greasy Fork syncs.
- Other userscript hosts, such as OpenUserJS.
- A README install badge. Add it once the listing exists, as a separate change.
- Auto-rollback. Greasy Fork keeps old versions; a bad release is fixed forward.

## Constraints

- Greasy Fork has no upload or publish API. The supported automation is a
  release sync, configured once in Greasy Fork and in the GitHub repository.
- The Greasy Fork sync URL must be
  `https://github.com/fran2889/flix-monkey/releases/latest/download/FlixMonkey.user.js`.
  The release asset must be named exactly `FlixMonkey.user.js`, which
  `release-please.yml` already uploads.
- The GitHub webhook is a repository setting that needs the secret generated by
  Greasy Fork. The workflow cannot create it without that secret, so the setup is
  manual and one-time.
- The `release` webhook fires when release-please finalizes the draft release,
  which happens before a maintainer runs `Publish to Stores`. The manual
  workflow verifies the result; it does not cause it.
- The verification job is read-only. It needs `GITHUB_TOKEN` for the release
  download and the public Greasy Fork script ID. It needs no Greasy Fork
  credentials.
- `GREASYFORK_SCRIPT_ID` is a repository variable, not a secret. The script ID is
  public.
- All actions stay SHA-pinned, and the workflow must pass `actionlint`.
- A failed check is explicit and recoverable by re-running only that job. Do not
  add retries to hide a missed webhook.

## Approaches considered

1. **Release webhook sync with a one-shot verification job (chosen).** Configure
   the Greasy Fork listing once, add the GitHub `Releases` webhook, and add a
   `publish-greasyfork` job that checks the released asset and the Greasy Fork
   version once. The job makes the manual publish run the place where all three
   channels are confirmed, without putting Greasy Fork credentials in CI.
2. **Release webhook sync, documentation only.** The simplest option, but the
   publish flow gives no signal when the webhook or listing is broken.
3. **Playwright-driven upload from the manual workflow.** Real
   publish-on-dispatch, but unofficial, brittle, dependent on session cookies
   and 2FA, and a poor fit for the existing store jobs. Rejected.

Option 1 was chosen with no polling, so the job reports the state at the time of
the run instead of waiting for Greasy Fork.

## Decisions

### One-time setup

1. On Greasy Fork, import
   `https://github.com/fran2889/flix-monkey/releases/latest/download/FlixMonkey.user.js`
   and keep the default `Automatic` sync type. The first release webhook changes
   the listing to `Webhook` sync.
2. Record the numeric script ID from the listing URL
   (`https://greasyfork.org/en/scripts/<id>-...`).
3. Store the ID as the repository variable `GREASYFORK_SCRIPT_ID`.
4. On `https://greasyfork.org/en/users/webhook-info`, note the payload URL and
   generate the webhook secret.
5. In the GitHub repository, open Settings, Webhooks, Add webhook. Set the
   payload URL, content type `application/json`, the generated secret, and choose
   `Let me select individual events` with `Pushes` unchecked and `Releases`
   checked. Leave the webhook active.
6. Confirm the ping delivery succeeds.

### `publish-greasyfork` job

- Runs in parallel with `publish-chrome` and `publish-firefox`, so a Greasy Fork
  failure does not block the stores and each job can be re-run on its own.
- Uses `timeout-minutes: 5`, `ubuntu-latest`, and the workflow's existing
  `permissions: contents: read`.
- Does not check out the repository and does not install Node or run
  `npm ci`. It uses the preinstalled `gh` and `curl` only. It sets `GH_REPO` to
  `${{ github.repository }}` so `gh release download` resolves the repository
  without a checkout.
- Validates the tag with the same `^v[0-9]+\.[0-9]+\.[0-9]+$` check as the other
  jobs.
- Downloads the released userscript with
  `gh release download "$TAG" --pattern "FlixMonkey.user.js" --dir dist`.
- Reads `@version` from the downloaded userscript and fails if it does not match
  the tag without its `v` prefix. This isolates a broken release from a stale
  Greasy Fork listing.
- Fetches `https://update.greasyfork.org/scripts/<id>.meta.js` once, with
  `--max-time 30` and a `Cache-Control: no-cache` request header, reads
  `@version`, and fails if it does not match the expected version.
- On a version mismatch, prints both versions and tells the maintainer to check
  the webhook delivery and the listing sync URL, then re-run the job.
- When `GREASYFORK_SCRIPT_ID` is unset, fails before contacting Greasy Fork with
  a message naming the variable.

The version line is read with:

```bash
sed -n 's|^[[:space:]]*//[[:space:]]*@version[[:space:]]*||p' <file> | head -n 1 | tr -d '\r'
```

### Documentation

- `docs/STORE_PUBLISHING.md`: add Greasy Fork to the intro, the artifact list,
  the overview, and the publishing steps. Add a Greasy Fork setup section and a
  repository variable section. Document the check and its failure behavior.
- `CONTRIBUTING.md`: mention Greasy Fork in the store-publishing pointer.
- `AGENTS.md` Releases: state that Greasy Fork is updated by the GitHub release
  webhook and verified by `publish-to-stores.yml`.
- No README change until the listing exists.

## Failure handling

- Missing release asset, or a released userscript whose `@version` differs from
  the tag: fail before contacting Greasy Fork, naming the asset and both
  versions.
- Unset `GREASYFORK_SCRIPT_ID`: fail with the variable name and the setup
  section reference.
- Greasy Fork unreachable, non-2xx, or slower than 30 seconds: fail with the
  endpoint and curl's error.
- Greasy Fork serving a different version: fail with both versions. The
  maintainer checks the webhook delivery and the listing sync URL, then re-runs
  the job.
- No retry. A re-run is deliberate.

## Verification

- `actionlint` passes on the edited workflow, and Prettier and markdown checks
  pass.
- The version extraction returns `1.7.0` for the released `v1.7.0` userscript.
- After the listing exists and the variable is set, a workflow run for an
  ingested tag passes.
- Running against a tag whose version Greasy Fork has not ingested fails with
  the expected-versus-actual message.
- A run with `GREASYFORK_SCRIPT_ID` unset fails before the Greasy Fork request.
- Confirm the Chrome and Firefox jobs are unaffected.

## Risks and maintenance

- Greasy Fork can change or block the public meta endpoint, or block CI
  addresses. The job then fails even though the sync is healthy. The failure is
  explicit, and the fix is to verify manually and adjust the endpoint.
- The check runs once. If the webhook is delayed, the run fails and the
  maintainer re-runs later.
- The release asset name `FlixMonkey.user.js` is now a contract with Greasy Fork.
  Renaming it requires updating the listing sync URL.
- The GitHub webhook and its secret live outside the repository, so the setup is
  not reproducible from code. Keep the runbook current.
- The workflow cannot repair a missed webhook delivery. It only reports it.

## What's left to the builder

- Add the job to `publish-to-stores.yml`, following the existing job layout and
  indentation.
- Choose the final error wording.
- Update the three documentation files.
- Keep the job free of checkout, Node, and npm setup.
- Add the README Greasy Fork install link in a follow-up once the listing exists.
